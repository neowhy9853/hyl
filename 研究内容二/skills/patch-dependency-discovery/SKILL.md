# 前置依赖发现

输入只有原补丁 A 时，找到可能提供缺失能力的提交 B，并区分“参考实现依赖 B”和“目标修复必须迁移 B”。模型决定每次查询、候选筛选和语义结论，Git 工具提供可复查证据。

## 输入与结果

必需：`reference_patch`、`target_repo`（同仓库可用 `repo`）、`target_ref`、`output_dir`。历史发现还需 `reference_repo`（默认同仓库）、`reference_fix` 或可确定的 `reference_parent`；没有参考历史时可分析已给代码，但具体提交发现保留缺项。

可提供：失败日志、缺失符号/行为、已有迁移分析、仓库范围元数据，以及用户是否允许引入新功能。结合失败日志形成检索线索，并使用代码证据确认依赖。

开始时阅读 [结果契约](references/discovery-contract.md)。在同一 output_dir 下，调查中写 `details/dependency-evidence.json`，完成后写 `details/dependency-discovery.json`，查询输出放入 `details/dependency-observations/`；最终返回同一合法 JSON。使用实际绝对路径引用证据，只在调用本阶段时创建文件。结果绑定两仓库、完整 SHA 和参考补丁哈希，便于调用方判断是否仍适用。

## 1. 将失败转换成能力问题

读取 A 的实际 diff、修复前实现及相关调用路径，列出它需要的函数、字段、初始化、锁协议、输入校验或资源生命周期约定。每项记录 `required_capability` 及使用位置。

先分流：

- 缺少 make、编译器、系统库或网络下载失败：环境问题，不检索成源码依赖提交。
- 路径不存在、函数改名、签名变化：先找目标等价实现，不能直接补入旧代码。
- 仅 hunk 上下文偏移：先检查文本适配，无语义缺口则不推断前置依赖。
- 当前候选遗漏了 A 自己新增的声明/调用点：回到实施修正，不另找前置提交。

## 2. 确认目标缺口

检查精确 target 的实际源码、定义、调用者、构建条件和相关入口。判断 `present_equivalent`、`present_incompatible`、`absent` 或 `unknown`。

没有同名文件只支持“同名文件不存在”。功能整体不存在时，还需调查目标是否有等价危险行为；把源码功能、配置是否启用和运行环境工具分开判断。目标暴露面不清楚时保留 `unknown`，交迁移分析判断，不自行宣告 `no_change`。

跨仓库在 reference_repo 找能力来源，在 target_repo 核对语义等价；提交 SHA 与路径始终注明所属仓库，不建立虚构共同历史。

## 3. 从能力检索候选提交

按当前线索阅读 [历史检索指引](references/history-search.md)，查询文件引入、符号变化、调用者及相关历史。

- 搜索范围以允许的 reference parent 祖先为起点，发现分支或重写时由模型选择下一条父子边。
- 对每个命中读取父子 diff 和两侧实现，判断是首次提供、后续修正、移动还是删除；候选确认需要父子版本的代码证据。
- A 需要的是 API 的具体语义版本，不一定是首次出现同名符号的提交。
- 记录排除理由；候选有多个时保留竞争解释，不按时间或文本相似度直接选择。
- 查询截断就记录范围并继续分页或缩小问题。无新证据、历史缺失或范围限制时停止并保留 unresolved，不把未完成搜索说成依赖不存在。

## 4. 核验关系与目标必要性

对候选 B 建立三项证据：

1. A 在哪个路径实际使用了该能力；
2. B 的新增或修改怎样提供该能力；
3. 目标为什么没有等价实现，或为何已有实现不能安全替代。

部署了 `patch-relation-analysis` 时，先完整读取并调用它，以 A 为 commit_a、B 为 commit_b；将其最终语义结果作为关系证据。仅有提取脚本的 `unrelated`/零分表示未发现显式标记，不能覆盖代码依赖证据。

未部署关联性 Skill 时，按上面的三项证据完成模型代码复核，记录 `verification_method=model_code_review`；不要声称已调用关联性 Skill。需要额外关系证据但无法取得时记录 unknown。

分别输出：

- `reference_dependency`：B 是否提供 A 依赖的代码/行为；
- `target_port_requirement`：目标是否需要迁移、可就地适配、已有等价能力，或需要先批准功能扩展。

“B 引入被修复功能”不等于“原目标必须引入整个 B”。检查 B 中必要修改与无关重构，能用目标已有机制适配就提出替代方案；没有验证不可声称最小依赖集合。

## 5. 递归与交接

B 若依赖 C，使用同一方法核查 C。以仓库身份、提交和能力标识去重，检测循环；不得一次导入整个历史区间。发现依赖顺序仅输出经过证实的图，未解决节点单列。

本 Skill 只调查并写分析产物。将建议返回迁移分析：确认目标受影响、范围及完整实施计划后，才进入实施与独立验证。新功能引入未获授权时输出 `request_scope_approval`；历史/实现证据不足时输出 `collect_more_evidence`。

依赖被实施后，以原 target SHA 加有序补丁及累计哈希标识新基线，重新分析 A；不得沿用旧基线的就绪结论。构建工具缺失、补丁可应用、语义验证通过分别报告。

需要示例或检查判定边界时阅读 [案例与验收场景](references/examples.md)。
